# 二、问题清单（按严重程度）

## 🔴 P0 级：记忆完全依赖内存，关浏览器即丢

**问题位置**：`AgentController.java`

```java
/** 会话内记忆存放在 session 里的 key */
List<JsonNode> history = (List<JsonNode>) session.getAttribute(SESSION_HISTORY);
if (history == null) {
    history = new ArrayList<>();
    session.setAttribute(SESSION_HISTORY, history);
}
```

**影响**：

| 数据 | 存储位置 | 关闭浏览器后 |
|---|---|---|
| 对话历史 `history` | **HttpSession 内存** | **全部丢失** |
| GPS 位置 | **HttpSession**（注释写明"不落库"） | **全部丢失** |
| 行程 / 画像 / 同行人 | MySQL | 保留 |

**后果**：session 一失效，`history` 变成空列表，模型看不到任何上文 → 用户每次进来都是全新对话。

---

## 🔴 P0 级：`MAX_ROUNDS = 6` 导致"读得到但写不回去"

**问题位置**：`TravelAgentService.java`

```java
private static final int MAX_ROUNDS = 6;
```

**一次"行程变更"的完整链路**：

```
listPreferences（画像）      → 轮1
listTripNodes（现有节点）     → 轮2
查开放 / 预约时间             → 轮3
算时间是否来得及              → 轮4（可能还要 searchWeb 查备选）
saveTripNode（写回行程）      → 轮5
setTripStatus / 输出风险清单  → 轮6  ← 刚好用完
```

**后果**：6 轮刚好够"读一遍"，不够"算一遍 + 写回去"。模型倾向于**只输出一段文字建议，而不真正改数据** → 用户点进「行程」页面看，一个字都没变。

---

## 🔴 P0 级：Agent 改了数据，但界面只有聊天气泡

**问题**：Agent 通过工具真实写库后，`/agent/chat` 只返回纯文本：

```java
@PostMapping(value = "/agent/chat", produces = "text/plain;charset=UTF-8")
public String chat(...) { ... return answer; }
```

**后果**：

```
用户说"帮我记住我不吃辣"
   ↓
后端：savePreference(username, "饮食忌口", "不吃辣")   ← 真写了库
前端：一个聊天气泡「好的，已记住您不吃辣」              ← 只有文字
用户：没有任何界面能验证 → 无法确认它到底做没做
```

**30 个工具的调用过程零可见性。**

## 🔴 P0 级：偏好画像有 7 个写接口，却没有读接口

**问题位置**：`PreferenceTemplateController.java`

**改造前已有的接口**：

```java
@PostMapping("/preference/template/list")
@PostMapping("/preference/template/save")
@PostMapping("/preference/template/copy")
@PostMapping("/preference/template/delete")
@PostMapping("/preference/template/activate")
@PostMapping("/preference/item/save")
@PostMapping("/preference/item/delete")
```

**前端 `chat.html` 实际调用的接口**：

```
agent/available · agent/location · agent/chat · destinations
myinfo · updateUserInfo
trips/save · trips/list · trips/get · trips/delete
```

> 🔴 **`preference/*` 一个都没调。**

**而且**：`user_preference` 表（Agent 对话实际读取的"当前生效画像"）**没有对应的读取接口** —— 只有写入口。

**界面上关于"偏好"的全部内容只有四处**：

| 位置 | 内容 |
|---|---|
| `:1272` | 弹窗副标题："更新您的账户安全信息和**旅行偏好**设置"（只是一句话） |
| `:1484` | 快捷入口 `{id:'pref', icon:'fa-heart', title:'记住偏好'}` |
| `:1495` | 欢迎语里提到"**记住你的旅行偏好**" |
| `:1762` | 点了那个入口 → **只发一条文本** `this.sendText('我想设置我的旅行偏好')` |

**外加提示词明确要求"静默更新画像"** —— 三个"静默"叠加，用户永远感觉不到它在记。

## 🟠 P1 级：`/Aichat` 与 `/agent/chat` 并存，静默降级

**问题位置**：`chat.html` + `AgentController.java`

```js
const res = await fetch(ready ? 'agent/chat' : 'Aichat', { ... });
```
```java
result.put("available", loggedIn && configured);
```

| 接口 | 实现 | 能力 |
|---|---|---|
| `/Aichat` | `AiChatService.chat()` | 一次问答，**无工具、无循环** |
| `/agent/chat` | `TravelAgentService.run()` | 有循环、30 个工具 |

**后果**：未登录或未配 API Key 时**静默降级**。降级后用户看不出区别（都是聊天气泡），但此时**所有 Agent 能力全部失效**。

> ⚠️ **最危险的一条**：如果 API Key 没配好，会用旧的桩回复测整个产品，然后得出"产品不行"的结论 —— 调试方向完全错误。

# 三、本次改造内容

| 组 | 改动 | 文件 |
|---|---|---|
| **A** | 对话历史落库 | `AgentSchemaInitializer`（新增 `chat_message` 表）· **新建** `ChatMemoryRepository` · `AgentController`（去掉 session history，新增 `/agent/history`）· `chat.html`（新增 `loadHistory`） |
| **B** | AI 动作可见 | `TravelAgentService`（新增 `AgentResult` + 15 个写操作的摘要）· `AgentController`（`/agent/chat` 改返回 JSON）· `chat.html`（动作卡片样式 + 渲染） |
| **C** | 偏好可见 | `PreferenceTemplateController`（**新增 3 个接口**：`/preference/list`、`/preference/item/save-current`、`/preference/item/delete-current`）· `TravelAgentService`（提示词：静默 → 回显）· `chat.html`（**新增「我的偏好」面板**） |
| **D** | 参数调优 | `TravelAgentService`（`MAX_ROUNDS` 6→12 · 提示词最前加 5 条铁律 · 末尾加四引擎速查段） |

## 关键设计决定

| 决定 | 理由 |
|---|---|
| **历史只存 user/assistant 纯文本** | 回放 `tool_calls` 容易触发「没有对应 tool 响应」的 400 报错 |
| **只对 15 个写操作生成摘要** | 读类工具生成摘要会刷屏 |
| **写操作摘要解析失败返回 null** | 宁可少显示一条，也不要让摘要逻辑把回答流程弄坏 |
| **`/agent/chat` 保留 `String` 版 `run()` 方法** | 不破坏其他调用方 |
| **偏好接口 `where username = ?` 双条件** | 即使前端伪造 tag 也删不到别人的画像 |

## 验收标准

**A 组**：关掉浏览器 → 重开 → 问「我们刚才聊到哪了？」→ **应能接上**

**B 组**：说「帮我记住我不吃辣」→ **聊天气泡下方应出现蓝色卡片**；说纯查询 → **不应出现卡片**

**C 组**：说「我不吃辣、我走不了太久」→ 回答末尾出现 `📌 已记住：…` → 打开「我的偏好」**应看到这两条** → 刷新**仍在** → 手动删掉「不吃辣」→ 再问行程 → **不再推荐辣菜**

**D 组**：说「帮我把第二天上午的改成 XX」→ **打开行程页面确实变了**

# 五、一句话总结

> **改造前的产品完成了 77% 的后端能力，却只展示了 23%。**
>
> **四个 P0 问题叠在一起的效果是：记不住（历史在内存）、改不动（轮数不够）、看不见（偏好无读接口）、没法验证（动作不可见）。**
