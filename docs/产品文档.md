# LTing 出行Agent · 产品文档

> 记录这个产品的定位、核心决策与取舍依据。

---

## 一、产品定位

**一句话**：一个能对话规划行程、并把每一件旅行资产沉淀下来的 AI 管家。

**不做什么**：不做景点百科、不做通用游记生成器、不做「一张表格攻略」。

**判断依据**：问「XX 有什么好玩」这类问题，通用大模型答得比我好。
**我能做得比它好的，是「记住这个人、并让方案可执行」。**

## 二、用户问题

| # | 问题 | 现状 |
|---|---|---|
| 1 | **聊完就丢** | 通用 AI 助手关掉页面什么都不剩 |
| 2 | **说了不做** | AI 说「已记下」但用户无法验证 |
| 3 | **通用问答答不到落地** | 问「附近吃啥」得到一堆没有具体店名的品类 |
| 4 | **行程变化后无法顺延** | 静态攻略文档改一处就全乱 |
| 5 | **多人出行偏好冲突** | 每个人的诉求没法对齐到一份行程 |

## 三、6 个核心产品决策

### 决策 1：行程节点化，不做一坨文本

**做法**：`trip_node` 表存时间线节点（订单 / 预约 / 风险 / 备注 / 备选路线），而非一段 Markdown。

**理由**：用户说「起晚了」，如果行程是一段文本，AI 只能重写整段；
节点化之后才能**只改受影响的节点并顺延后续**。

### 决策 2：给行程做版本快照

**做法**：`trip_version` 表 + `rollbackTrip` 一键回退。

**理由**：AI 改行程是有风险的。**用户敢用自动化，前提是知道能撤回。**

### 决策 3：偏好写入必须回显

**做法**：`savePreference` 之后，回答末尾固定输出「📌 已记住：维度=取值」。

**理由**：从「静默记忆」改成「可见记忆」。
**记忆看不见，用户就不信它有记忆** —— 这是踩过的坑。

### 决策 4：写操作要在界面上可见

**做法**：`/agent/chat` 除了 `answer` 还返回 `actions` 数组，前端渲染成卡片。

**理由**：Agent 真的写库了，但用户只看到一个聊天气泡 → 他会怀疑「它到底做了没有」。
**只给 15 个写操作生成摘要，读操作不生成**，避免刷屏。

### 决策 5：多会话隔离，避免上下文污染

**做法**：`chat_session` 表 + 新建 / 列表 / 重命名 / 删除，首条消息自动起标题。

**理由**：只有一个长会话时，聊到第五个话题上下文全是噪音。
**会话级记忆解决「关掉还能接上」，多会话解决「想开个新话题」。**

### 决策 6：空间问题必须报真实距离

**做法**：`searchNearby` 基于 session 里上报的真实 GPS 算距离，输出「约 1.2 公里（建议打车）」。

**理由**：模型容易把几公里外的店说成「附近」。
**涉及空间就报米数**，这是可信度的底线。

**安全约束**：坐标只从 session 取，**模型无权指定** —— 否则「附近」就成了模型随便挑的一个点。

## 四、功能范围

### 已实现

| 模块 | 内容 |
|---|---|
| 智能管家 | 30 个工具 · 12 轮循环 · 四大引擎 |
| 多会话 | 新建 / 列表 / 重命名 / 删除 / 自动标题 |
| 动态广场与好友 | 公开 / 仅好友 / 仅自己 · 广场聚合 · 好友（ID 或邀请码）· 他人主页按权限过滤 |
| 行程本 | 行程 · 时间线节点 · 版本快照与回退 · 状态流转 · **预算绑定对应行程** · 行李清单 |
| 打卡 | 地点 / 评分 / 耗时 / 备注 · 配图 · **可关联附近商户**（记录同步写入该商户详情页）· 与动态相互独立 |
| 游记生成 | 基于打卡记录生成结构化游记 |
| 附近吃喝玩乐 | 5–10km **不设上限** · 评分 / 菜单 / 真实评价 · 一键导航（内嵌）· 大众点评入口（内嵌，按店名+城市搜） |
| 偏好档案 | 饮食 / 体力 / 环境 / 出行四类**硬约束** · 忌口食材 · 画像标签 · 多套模板 |
| 个人资料 | 头像 / 昵称 / 标签 / 简介 / 兴趣偏好 · 同行人 · 证件票据 |
| 账号管理 | 修改密码 · 绑定 / 更换 / 解绑邮箱 · 注销账号（连同全部数据） |
| GPS 现场向导 | 逆地理 · 周边检索 · 路径规划 · 到达播报 |
| 桌面端 | Electron 外壳 · 内嵌地图 · 自动拉起后端 · **自带 jlink 裁剪的 JRE 与内嵌数据库，对方免装 Java/MySQL** |
| 会话持久化 | 会话写 MySQL，重启恢复登录态 |

### 明确不做

| 不做 | 理由 |
|---|---|
| 景点百科 | 通用大模型更强 |
| 通用游记生成器 | 差异化不足 |
| 无人值守自动化下单 | 涉及支付，风险不可控 |
| 接 MCP / Agent 框架 | 30 个工具直接写 Java 更可控 |

## 五、优先级依据

排序标准：**用户能立刻感觉到差别 > 技术上有意思**。

| 优先级 | 功能 | 理由 |
|---|---|---|
| P0 | 对话历史落库 | 不落库一切都白搭 |
| P0 | 会话持久化 | 关掉软件就丢，用户直接不用了 |
| P0 | 写操作可见 | 建立信任的最短路径 |
| P1 | 多会话 | 解决上下文污染 |
| P1 | 偏好可见 | 让「记忆」变成可验证的事 |
| P2 | 游记 / 工具箱界面 | 有价值但不影响主流程 |

## 六、已知缺陷

| # | 缺陷 | 影响 |
|---|---|---|
| 1 | **密码明文存储** | 安全隐患，应改 BCrypt |
| 2 | **30 个工具未合并** | 超出模型有效选择范围，深层工具不易触发 |
| 3 | **自动登录未实现** | 勾选框读 `value` 而非 `checked` |
| 4 | **多个功能有后端无界面** | 游记 / 时间线 / 版本回退 / 同行人 |
| 5 | **无单元测试** | 全靠手工验证 |

## 七、可复用的产品方法论

这个项目沉淀出的、可以迁移到其他 AI 产品的做法：

1. **AI 改了数据，界面必须显示改了什么** —— 否则用户不信
2. **记忆要可见** —— 「静默记忆」等于没有记忆
3. **写操作和读操作要有不同的反馈** —— 读操作刷屏会淹没写操作
4. **给自动化留退路** —— 版本快照、可回退
5. **空间/数量类回答要给可验证的数值**（米数、金额），不要模糊词
6. **把「用户是谁」「聊过什么」「有几个话题」拆成三层存**
