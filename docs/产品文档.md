# LTing 出行Agent · 产品文档

> 记录这个产品的定位、核心决策与取舍依据。

**核心主线**：目的地与时间 → 点击候选地点 → 规则校验 → Preview → 用户确认 Apply → 版本回退。
附近、地图、社交与旅途记录继续保留，但主叙事已经从聊天优先转为 Click-first。

**版本**：桌面版 `2.0.2`（2026-11-18）

---

## 一、产品定位

**一句话**：一个用户通过点击做选择、由规则引擎保证可行、由 AI 执行结构化修改的 Agent 旅行工作台。

**不做什么**：不做景点百科、不做通用游记生成器、不做「一张表格攻略」，也不把没有官方授权的点评平台抓取包装成底层接口。

**判断依据**：空白聊天框把需求组织成本推给用户；模型生成文本又难以校验、修改和回退。
LTing 的差异化不是“聊得更像”，而是让地点选择、规则校验、Agent 修改和版本恢复进入同一个可执行闭环。

---

## 一点五、Type-first → Click-first

| 维度 | 1.x Type-first | 2.x Click-first |
|---|---|---|
| 第一入口 | 聊天输入框 | 目的地、时间、候选点和行程工作台 |
| 用户动作 | 描述需求后等待 | 点击类型、区域、地点和行程节点 |
| AI 角色 | 主要生成者 | 自由表达、异常处理、规则解释和 Operation 生成者 |
| 修改方式 | 文本重写或工具直写 | Context → Preview → Apply |
| 失败处理 | 重新描述 | 结构冲突可见，可调整或回退 |
| 状态保存 | 对话和部分资产 | 同一份 canonical trip state + 版本链 |
| 信任来源 | 回答看起来合理 | 每步可执行、可验证、可撤销 |

## 二、用户问题

| # | 问题 | 现状 |
|---|---|---|
| 1 | **聊完就丢** | 通用 AI 助手关掉页面什么都不剩 |
| 2 | **说了不做** | AI 说「已记下」但用户无法验证 |
| 3 | **通用问答答不到落地** | 问「附近吃啥」得到一堆没有具体店名的品类 |
| 4 | **行程变化后无法顺延** | 静态攻略文档改一处就全乱 |
| 5 | **多人出行偏好冲突** | 每个人的诉求没法对齐到一份行程 |

## 三、10 个核心产品决策

### 决策 1：行程节点化，不做一坨文本

**做法**：`trip_node` 表存时间线节点（订单 / 预约 / 风险 / 备注 / 备选路线），而非一段 Markdown。

**理由**：用户说「起晚了」，如果行程是一段文本，AI 只能重写整段；
节点化之后才能**只改受影响的节点并顺延后续**。

### 决策 2：给行程做版本快照

**做法**：`trip_version` 表 + `rollbackTrip` 一键回退。

**理由**：AI 改行程是有风险的。**用户敢用自动化，前提是知道能撤回。**

### 决策 3：偏好写入必须回显

**做法**：`savePreference` 之后，回答末尾固定输出「📌 已记住：维度=取值」。

**理由**：从「静默记忆」改成「可见记忆」。
**记忆看不见，用户就不信它有记忆** —— 这是踩过的坑。

### 决策 4：写操作要在界面上可见

**做法**：`/agent/chat` 除了 `answer` 还返回 `actions` 数组，前端渲染成卡片。

**理由**：Agent 真的写库了，但用户只看到一个聊天气泡 → 他会怀疑「它到底做了没有」。
**只给 15 个写操作生成摘要，读操作不生成**，避免刷屏。

### 决策 5：多会话隔离，避免上下文污染

**做法**：`chat_session` 表 + 新建 / 列表 / 重命名 / 删除，首条消息自动起标题。

**理由**：只有一个长会话时，聊到第五个话题上下文全是噪音。
**会话级记忆解决「关掉还能接上」，多会话解决「想开个新话题」。**

### 决策 6：空间问题必须报真实距离

**做法**：`searchNearby` 基于 session 里上报的真实 GPS 算距离，输出「约 1.2 公里（建议打车）」。

**理由**：模型容易把几公里外的店说成「附近」。
**涉及空间就报米数**，这是可信度的底线。

**安全约束**：坐标只从 session 取，**模型无权指定** —— 否则「附近」就成了模型随便挑的一个点。

### 决策 7：从 Type-first 改为 Click-first

**做法**：用户先选择目的地、时间、候选和节点，AI 不再承担“把空白输入变成完整行程”的唯一职责。

**理由**：旅行是大量选择和取舍，不是一次文本生成。点击让状态明确、可校验、可连续修改；AI 用来处理自由表达和复杂操作。

### 决策 8：所有修改进入 PlanOps

**做法**：点击和 AI 都只能生成结构化 Operation，先 Preview，用户确认后 Apply，并生成前后版本。

**理由**：如果 AI 能直接写 `plan_data`，规则、审计和回退都会绕过。执行入口统一后，风险控制和 UI 回执才有唯一事实源。

### 决策 9：候选池是一等对象

**做法**：候选独立于正式行程保存、筛选和版本化；用户先“想去”，再决定如何排。

**理由**：旅行规划的核心不是立刻生成三天行程，而是先看足够多、足够准的吃喝玩乐地点。

### 决策 10：多源聚合，但不抓取无授权平台

**做法**：高德为主，百度/腾讯按商用 Key 可选，地方文旅和公共数据自动补充；美团、点评、抖音、小红书只在取得正式接口后接入。

**理由**：数据丰富不能以授权、反爬和稳定性风险为代价。没有来源和授权的数据，不适合做产品底层。

### 明确不做

| 不做 | 理由 |

| 景点百科 | 通用大模型更强 |

## 五、优先级依据

排序标准：**用户能立刻感觉到差别 > 技术上有意思**。

| 优先级 | 功能 | 理由 |
|---|---|---|
| P0 | 对话历史落库 | 不落库一切都白搭 |
| P0 | 会话持久化 | 关掉软件就丢，用户直接不用了 |
| P0 | 写操作可见 | 建立信任的最短路径 |
| P1 | 多会话 | 解决上下文污染 |
| P1 | 偏好可见 | 让「记忆」变成可验证的事 |
| P2 | 游记 / 工具箱界面 | 有价值但不影响主流程 |

## 六、已知缺陷

| # | 缺陷 | 影响 |
|---|---|---|
| 1 | **密码明文存储** | 安全隐患，应改 BCrypt |
| 2 | **百度/腾讯真实 Key 字段未验收** | 需要目标账号下验证配额、字段和坐标 |
| 3 | **OSM/维基公共接口不稳定** | 无 SLA，失败时静默降级 |
| 4 | **消费级发现页尚未实现** | 当前仍是工作台，不是美团/点评式内容流 |
| 5 | **住宿具体酒店和房价暂缓** | 目前只有区域与通勤评分 |

## 七、可复用的产品方法论

这个项目沉淀出的、可以迁移到其他 AI 产品的做法：

1. **AI 改了数据，界面必须显示改了什么** —— 否则用户不信
2. **记忆要可见** —— 「静默记忆」等于没有记忆
3. **写操作和读操作要有不同的反馈** —— 读操作刷屏会淹没写操作
4. **给自动化留退路** —— 版本快照、可回退
5. **空间/数量类回答要给可验证的数值**（米数、金额），不要模糊词
6. **把「用户是谁」「聊过什么」「有几个话题」拆成三层存**
