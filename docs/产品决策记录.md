> 设计文档讲"怎么实现"，产品文档讲"做什么"，这份讲"为什么"。

## 决策 1：行程节点化，不做一坨文本

**问题**：行程怎么存？最容易的写法是把 AI 生成的方案整段存进一个 `content` 字段。

**为什么不用整段文本**：

| 场景 | 整段文本 | 节点化 |
|---|---|---|
| 用户说「起晚了 2 小时」 | AI 只能**重写整段**，前面确认过的内容也可能变 | 只改受影响的节点，**顺延后续** |
| 用户问「第二天上午是什么」 | 要从文本里解析 | 直接查 |
| 想标记「这个票要退」 | 没地方放 | `risk` 类型节点 |

**采用方案**：`trip_node` 表，节点类型分五类：
`order`（订单）· `booking`（预约）· `risk`（风险）· `note`（备注）· `route`（备选路线）

**代价**：
- AI 要多次调用工具才能拼出行程（`listTripNodes` → 算 → `saveTripNode`）
- 这正是后来把 `MAX_ROUNDS` 从 6 提到 12 的原因

**收益**：**行程变成可局部修改的对象，而不是一次性文档。**

## 决策 2：给行程做版本快照 + 一键回退

**问题**：AI 改行程是有风险的。用户凭什么敢让它改？

**采用方案**：`trip_version` 表，每次修改自动存一版；`rollbackTrip` 一键回退。

**关键点**：**这个功能提示词里根本没要求做。**

是我在设计时加的一个判断：

> **用户敢用自动化，前提是知道能撤回。**

这跟编辑器要有 Undo 是同一个道理 —— 不是因为用户会频繁撤销，
而是**因为存在撤销，用户才敢输入**。

**代价**：每次修改多一次写库；版本表会增长。

**收益**：把「AI 改行程」从"有风险的操作"变成"可试的操作"。

## 决策 3：写操作必须在界面上可见

**问题（踩过的坑）**：Agent 通过工具真实写了数据库，
但前端只显示一个聊天气泡 —— **用户无法确认它到底做没做**。

```
用户说"帮我记住我不吃辣"
   ↓
后端：savePreference(username, "饮食忌口", "不吃辣")   ← 真写了
前端：一个气泡「好的，已记住您不吃辣」                 ← 只有文字
用户：没有任何界面能验证 → 不信
```

**采用方案**：`/agent/chat` 除了 `answer` 还返回 `actions`：

```json
{
  "answer": "...",
  "actions": [{"tool": "savePreference", "summary": "记住偏好：饮食忌口 = 不吃辣"}],
  "sessionId": 12
}
```

前端渲染成卡片「🔧 本次为你做了 N 件事」。

**关键的子决策：只给 14 个写操作生成摘要。**

| 方案 | 后果 |
|---|---|
| 所有工具都生成摘要 | 一次查询就产生 5-6 张卡片，**刷屏，反而没信息量** |
| **只给写操作生成** ✅ | 卡片一出现就是"真的改了东西" |

**收益**：卡片成了**可信度信号** —— 出现就是真做了事。

## 决策 4：记忆从「静默」改成「可见」

**问题（踩过的坑）**：系统提示词原本写的是「从对话中自动提取偏好，**静默**更新画像」。

结果：**用户永远不知道它在记**。

**为什么"静默"是错的**：

> **记忆看不见，用户就不信它有记忆。**

这跟决策 3 是同一类问题：AI 做了事但不说，用户就当它没做。

**采用方案**：写入后固定回显，格式写死在提示词里：

```
📌 已记住：饮食忌口=不吃辣 · 步行耐受=低
```

**并加约束**：「一条回答最多回显 1 次，没有新增偏好时不要回显，禁止每轮都刷」。

**代价**：回答会长一行。

**收益**：**偏好从"后台数据"变成"用户可见的事实"。**

## 决策 5：三层会话存储

**问题（踩过的坑）**：原来对话历史只存在 `HttpSession` 内存里，
**关掉浏览器 / 重启后端即全部丢失** —— 用户回来发现"会话直接没了"。

**为什么不能只做一层**：三种数据的生命周期完全不同。

| 层 | 存什么 | 该活多久 |
|---|---|---|
| **HTTP 会话** `tomcat_sessions` | 你是谁（登录态） | 30 天，跨重启 |
| **话题** `chat_session` | 有哪几个话题 | 长期 |
| **消息** `chat_message` | 每个话题聊了什么 | 长期 |

**采用方案**：三层分开存。

**收益**：**任何一层失效都不影响另外两层。**
比如 HTTP 会话过期了，用户重新登录仍能看到全部历史话题。

**代价**：三张表要各自维护；查询时要先定位话题再取消息。

## 决策 6：多会话管理 —— 解决上下文污染

**问题**：只有一个长会话时，聊到第五个话题上下文已经全是噪音。

**采用方案**：`chat_session` + 新建 / 列表 / 重命名 / 删除 + **首条消息自动起标题**。

**为什么"自动起标题"这个细节重要**：

| 方案 | 后果 |
|---|---|
| 会话叫「会话 1 / 会话 2 / 会话 3」 | 用户根本认不出哪个是哪个，等于没有多会话 |
| **首条消息自动生成标题**（如「汕头4天游」）✅ | 一眼能找到 |

**收益**：**多会话从"技术上有"变成"真的能用"。**

## 决策 7：会话持久化用 JDBCStore，不用文件

**问题**：Tomcat 的会话持久化有两种：文件存储和数据库存储。

**为什么选数据库**：

| 方案 | 问题 |
|---|---|
| 文件存储 | 多实例部署时共享不了；文件损坏难排查；部署目录要可写 |
| **数据库存储** ✅ | 已有的 MySQL 直接用；状态可查可清理 |

**额外的好处**：**会话数据变得可观测** ——
可以直接 `select * from tomcat_sessions` 看有多少活跃会话。

**踩的坑**（已在设计文档记录）：
- 表必须自己建，`JDBCStore` 不会自建
- 列名要显式设置（Tomcat 9 是 `valid_session`，不是 `is_valid`）
- cookie 的 `maxAge` 必须在上下文初始化**之前**设置

## 决策 8：空间问题必须报真实距离

**问题（踩过的坑）**：模型很容易把几公里外的店说成「附近」。

**采用方案**：
- 提示词强制「报出米数，并据此说明步行可达还是需打车/骑行」
- 禁止用「附近」这种模糊说法
- 工具层用**真实坐标算直线距离**

**关键的安全约束**：

```java
// 坐标只认 session 里上报的 GPS，模型传什么都不作数
// 防越权 / 防编造坐标
```

**为什么这条必须写死**：如果允许模型指定坐标，
**「附近」就等于"模型随便挑的一个点"** —— 整个位置引擎失去意义。

## 决策 9：刻意不接 Agent 框架和 MCP

**问题**：做 Agent 要不要上 LangChain / MCP？

**采用方案**：**都不用**，自己写循环 + 工具注册表。

| 理由 | 说明 |
|---|---|
| **工具数量少** | 30 个工具用原生 Java `switch` 分发就够（`dispatch` 方法 110 行） |
| **可控性** | 引框架后出错要穿透两层抽象才能定位 |
| **依赖可控** | 少一个依赖就少一类版本冲突 |
| **MCP 不适用** | 工具全在自建库里，**直接写 Java 方法更简单**；工具超 10 个且要接第三方时才值得上 |

**这同样是产品判断**：**不是所有新技术都要往产品里堆。**

**代价**：工具多了以后 `dispatch` 会变成巨型 switch（现在已经有这个趋势）。

**这也是已知缺陷「30 个工具需合并到约 12 个」的由来。**

---

## 决策 10：不用 ORM

**采用方案**：原生 JDBC + `PreparedStatement`。

| 理由 | 说明 |
|---|---|
| **SQL 可见** | 排查问题时能直接看到执行的 SQL |
| **防注入** | 全部占位符，不做字符串拼接 |
| **越权防护明确写** | 所有按 id 查的 SQL 都显式带 `and username = ?` |

**最后一条是重点**：用 ORM 时容易写成 `findById(id)`，
**看起来没问题，但少了用户维度的约束** —— 改个 id 就能看别人的数据。

**手写 SQL 反而让这个约束显式可见。**

## 归纳：这个项目的五条产品原则

| 原则 | 体现 |
|---|---|
| **1. AI 改了数据，界面必须显示改了什么** | `actions` 卡片 |
| **2. 记忆要可见** | 偏好回显「📌 已记住」 |
| **3. 破坏性/不可逆的操作要有退路** | 行程版本快照 + 回退 |
| **4. 涉及空间与数量要给可验证的数值** | 报米数，不用「附近」 |
| **5. 新技术的取舍看收益，不看热度** | 不接 LangChain / MCP / ORM |
